# Plan 2: historical queries for newspaper evaluation

**Status: draft.** For developers connecting MCP's recorded game data to the [newspaper](../implementation.md). Depends on Plan 1's issue identity conventions; the renderer remains usable with fixtures during this work.

## Goal and success criteria

Query the existing dated records for a receiving civilization at a selected turn and supply the facts needed by Plan 3's story detectors. VD already runs MCP. Standalone evaluation reads MCP's SQLite database directly, using the same query and field-selection logic. Existing features and newspaper queries must share the extracted utilities, with their current live behavior preserved.

## Current state

`mcp-server/src/knowledge/store.ts` already stores dated player summaries, cities, and events. `getMutableKnowledgeHistory()` returns versions with optional player visibility filtering; `getMutableKnowledge()` selects the latest version. Historical queries need a cutoff and bounded comparison history.

`vox-agents/src/knowledge/database.ts` already provides `openReadonlyGameDb()`, archive path resolution, and metadata reads, used by Archivist and narrators. Its opener delegates to `agents/telemetry/sqlite-helpers.ts` and enables `ParseJSONResultsPlugin`. Archivist's `extractTurnContexts()` in `src/archivist/pipeline/extractor.ts` also selects the highest insertion ID per subject and turn, but loads the whole recording without receiver filtering.

The existing `get-players`, `get-cities`, and `get-events` MCP tools contain useful field restrictions inside their execution and formatting code. Their getters can refresh live data, and event formatting can discard IDs and values needed by detectors. The [visibility research](../research/research-visibility.md) describes these restrictions and their historical limitations.

The [data research](../research/research-data.md) identifies France in `f07b2f21-2d81-4eee-a3f5-d6d850081a25.db`, turns 125 to 175 and 200 to 300, as an initial evaluation candidate.

## Approach

Add newspaper evidence queries under `mcp-server/src/newspaper/` using an explicit `Kysely<KnowledgeDatabase>` connection. MCP calls them against its open database. Vox Agents opens the selected SQLite database read-only and imports the same compiled query and projection modules, without importing `knowledge/store.ts` or `server.ts`. Use the existing workspaces: MCP owns evidence and transport; Vox Agents owns replay orchestration and editorial, issue and render contracts. MCP must not depend on Vox Agents.

## Reuse and common utilities

Most connection, hosting, and rendering infrastructure can be reused directly. History selection and visibility need small extractions plus new historical behavior. The cutoff session, evidence contracts, replay controls, and source inspector are mostly new. As a rough planning estimate, existing code should cover about one third to one half of the implementation effort for this stage after extraction. This estimates avoided work, rather than a measured percentage of final source lines; historical permissions and the inspector are the main uncertainties.

Keep shared utilities with their domain owners. Generic field selection belongs in MCP `utils/`; history, visibility, and redaction remain under MCP knowledge, and pace remains under Vox Agents knowledge. Reuse the existing SQLite utilities in place. Move extracted implementations and their existing callers together, with no forwarding modules or new workspace package. Shared helpers depend on schema types and other pure helpers, without importing tool modules, live getters, or server startup. Projection and redaction return copies without mutating supplied rows or nested payloads.

Preserve the distinction between permission checks and presentation cleanup. `getPlayerVisibility()` currently returns full access when no summary is found, so newspaper projection must treat missing historical visibility as unknown and omit facts that require it. `cleanEventData()` removes `false`, `null`, and sentinel values and rewrites nested identifiers; event consolidation also drops individual IDs. Keep those operations on the existing tool presentation path. Capture source references before stripping metadata, and return permitted raw values to detectors and the inspector.

Preserve that presentation behavior for both existing event tools. Newspaper privacy must consider all representations of private terms and retain structured terms only when permitted. Resource redaction remains an existing `get-events` behavior; extracting it must not add a new redaction or live player-summary read to `get-diplomatic-events`.

Preserve the existing city tool's health formatting, boolean conversions, zero-to-sentinel conversions, and basic-visible `Wonders` behavior through its adapter. Its `IsCapital` schema entry currently has no populated value; extracting access rules must not change that output. Player projection similarly separates restrictions from static-info merging and display transformations such as relationship text cleanup.

Archivist's whole-recording extraction and Oracle's prompt replay remain separate workflows. Reuse their query patterns and underlying database utilities as described above. Their orchestration does not provide the receiver-specific cutoff session required here, and `ReplayWorkspace` reconstructs agent files rather than game evidence. Broader consolidation of those workflows is outside this stage.

Use type-only imports where only a type is needed. Evidence and replay contract schemas may depend on other browser-safe contract schemas; they must not pull database connections, query implementations, services or browser code into the shared contract boundary. During implementation, update `mcp-server/AGENTS.md` and `vox-agents/AGENTS.md` for these owners. Update `docs/developers/vox-agents/newspaper/replay.md` for startup through the normal VD server, read-only queries and inspector behavior, and `overview.md` in that directory for the MCP evidence and Vox Agents orchestration boundary.

A query takes the receiver, previous check, cutoff, and the comparison range needed by a detector, all in recorded game turns. Convert any pace-normalized detector duration once before querying. For each subject, select the latest applicable version at or before the cutoff, breaking same-turn ties by that table's insertion ID; include earlier versions when a comparison needs them. Select events within the requested turn range. Apply the receiver's recorded access and the selected fields before returning data to the editor.

Keep the result small: selected summary/city fields, relevant events, their existing IDs and turns, and the available condition values. These records are the editor's evidence. Source references point directly to database rows or events. Add result fields when a detector or the inspector needs them.

## Ordered implementation

1. **Extract and reconnect shared utilities.** Move generic field selection from Vox Agents report filters to MCP `utils/fields.ts` and update the existing wrappers. Extract MCP player/city access rules, resource redaction, and diplomatic subject metadata/matching, updating their existing tool callers in the same change. Keep tool adapters for display conversions, grouping, merged player information, live getters, and presentation cleanup. Reuse the existing read-only database opener in place. Establish behavior checks for the extracted rules before adding historical policy.

2. **Add historical queries.** Extract shared pure reads into `knowledge/history.ts` and have the existing store delegate while retaining failed-read refresh callbacks outside that module. Extract the event query from `get-events.ts`, preserving its exact-turn, type, ID-bound, visibility, and ordering behavior. Add separate cutoff and range reads for the summaries, cities, and events used by Plan 3. `newspaper/queries.ts` consumes those reads through its explicit typed connection. Define structural inputs/results/source references in `evidence.ts`. Add and register the `get-newspaper-evidence` MCP tool as the live-database adapter, with no refresh calls. Preserve missing values, row IDs, and original record dates. Use the existing schema types.

3. **Select reportable fields.** Compose the shared access, field-selection, resource-redaction, and event-subject helpers in `newspaper/projection.ts` with cutoff-specific context. Include own domestic and trade measures, permitted basic foreign-city facts, met civilizations' national culture/tourism, and supported public events, including war declarations involving the receiver. Extend existing diplomatic subject metadata only where supported nested payloads require it. Apply private-term policy to structured and readable deal terms together. Omit restricted facts when the required historical visibility is missing. Stored visibility levels determine access; new trade and espionage reporting grants extend this same policy module in Plan 5.

4. **Connect standalone evaluation.** Expose database path, receiver, turn range, and publication interval through the existing VD server, wired through `replay/database.ts`, `session.ts`, and `http.ts`. Open via the shared read-only knowledge helper, advance the cutoff for each check, and show records and source references. Keep settings and cursor in the session here; Plan 3 persists them with separate publication output. Register replay routes through `mountApplicationRoutes`, including their body parser, before the export host's fallbacks. Extend VD shutdown to stop new replay requests, drain accepted queries, then close the source connection; the existing export service retains its own queue and shutdown.

5. **Extend the existing browser shell.** Add `app/api.ts` and `replay.ts`; extract the current fixture inspection and link-detail rendering from `main.ts` into `inspector.ts`, then add evidence/source inspection there. Retain fixture mode and the shared publication reader. Evidence inspection must be usable before Plan 3 supplies generated issues.

6. **Supply conditions and comparisons as needed.** Query dated era, technology/policy events, and religion for the chosen templates. Leave unavailable conditions unknown so Plan 3 can use a broadly eligible design. Read recorded `gameSpeed` through the existing metadata helper and reuse the extracted metadata-only multiplier resolver. Use a recognized recorded game speed, then an explicit override, otherwise a labelled Standard assumption. Keep calculations in the story detectors: normalize route-yield sentinels, define denominators, and resolve route partners or city continuity only for stories that require them. Use existing city IDs by default; link a capture only when supporting records establish continuity.

## Risks and open questions

Older databases can have missing columns, stale city rows, or mixed save histories. Use a suitable recording for the initial evaluation and skip comparisons whose required data is unreliable. Missing historical unlocks may limit design transitions. The candidate still needs a verified merged-story and fade-and-return example for Plan 4.

## Out of scope

A general-purpose replay subsystem beyond this newspaper evaluation session, copied observation storage, recording fingerprinting or branch reconstruction, new live collection, trigger tuning, and article generation.
