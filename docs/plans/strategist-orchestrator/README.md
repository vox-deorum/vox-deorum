# Strategist Orchestrator: Staged Implementation Plan

This folder holds the strategist-orchestrator feature: the specification ([specs.md](specs.md)) and this staged implementation plan. Each numbered file is one stage with its objective, approach, work items, reuse, and verification. Implement in order. Each stage is independently verifiable, and the `null` workflow runs end-to-end at Stage 1, so no large untested chunk is left for the end.

This document is the **build-order outline**. It fixes the stages, their order, and each stage's expectation at completion. Individual stage plans are drafted later, one file each, in the house format (`## Objective` / `## Approach` / `## Work items` / `## Reuse` / `## Verify` / `## Done when`).

**Goal in one line:** a `scripted-strategist` runs a data-defined workflow through a real game exactly where a static strategist runs today, and an **offline orchestrator agent** reviews its recent runs and commits versioned edits to the workflow's script, manifests, and prompts. It never touches the run in flight and never reaches mcp-server.

## Context

Today a strategist is TypeScript compiled into the app. The spec turns a strategist workflow into **editable data**: a small control-flow script, per-sub-agent manifests, and templated prompts, run against the seat's existing file workspace. It then adds a **non-blocking orchestrator** that reviews recent runs and iteratively rewrites those artifacts to grow a seed into plausibly good variants. Workflows become improvable without recompiles, and an offline agent can debug and evolve them from real telemetry.

The spec is ambitious. This plan scopes a **maintainable v1**: it keeps the pieces that prove the whole pipeline end-to-end and **defers the machinery that is hard to change** until the loop has earned it. Each deferral leaves a clean seam.

## Already in place

The plan builds on infrastructure `vox-agents` already ships:

| Need | Existing code |
| --- | --- |
| Per-seat working folder | `WorkspaceStore` (`src/utils/workspace/workspace-store.ts`): a versioned SQLite store per seat with git-like commits. `PlayerWorkspace` mounts `records/` and `reference/` read-only, `game/` notes, `shared/<name>/` folders on disk that outlive a game, and a scratch `/tmp`. `materialize.ts` exports a seat to disk. |
| Game state as files | `SeatRecords` (`src/knowledge/records.ts`) writes each processed turn to `records/turn-N/` as Markdown plus JSON, and archives briefings through `recordBriefing`. |
| Script sandbox | just-bash `js-exec`, a QuickJS realm with a memory cap, a configurable timeout, TypeScript support, and fs bound to the workspace mounts. Its `invokeTool` hook exposes host functions to scripts as `tools.*`, and its `bootstrap` option runs setup code before each script. |
| Cached-token telemetry | Step and execution spans carry `tokens.input.cached` where the provider reports it (`src/infra/vox-execute.ts`, `src/utils/telemetry/model-usage.ts`). |
| Model tiers and effort | `modelTiers` (`small`/`default`/`large`) with `selectModelReference`, and the `@effort` suffix for reasoning effort. |
| Graceful step limits | `continuationNudge`, `stepsLeft`, and per-step `activeTools` narrowing in the agent loop. |
| Runs and concurrency | `VoxContext.withRun` and `forkRun`, and the staffed strategist's concurrent briefers. |
| Offline agent plumbing | The cached MCP tool definitions (`saveToolCache`/`loadToolCache` in `VoxContext`), the oracle retriever over telemetry spans, and conversation compaction in `executeAgent`. |

## Locked architecture decisions

These decisions shape the stages and are reflected in [specs.md](specs.md):

- **The orchestrator is a _type of agent_, like a strategist.** It is a registered agent with its own sub-agents and scoped file and git tools, driven offline by a console in the oracle/telepathist family.
- **The decision-quality judge is one pre-defined sub-agent the orchestrator can call.** It is deferred from v1, but a cheap add once the orchestrator-as-agent machinery exists. No separate judging subsystem is ever built.
- **just-bash `js-exec` is the script substrate.** Workflow scripts run in the QuickJS sandbox the player workspace already enables. Host primitives (sub-agent calls, actions, a keyed seeded index) come in through `invokeTool`, file grants are enforced by scoped filesystem views, and the memory cap and timeout bound plain compute. It needs no native build step, which matters on Windows.
- **Git-backed versioning.** The orchestrator-managed workflow folder is a git repository the orchestrator has scoped access to. A commit is a version snapshot, the message is the changelog, `git log` is the history, and a per-seat branch or ref is the `current` pointer the runtime reads once at run start. Adoption runs the gate, then advances the seat ref atomically. There is no automatic rollback: `git revert` is a deliberate edit.
- **One cost currency, over the normalized step counts.** Cost-weighted tokens are the single unit, with per-tier coefficients for cache reads, reads, and writes applied to the per-step counts the agent loop already computes and records on spans. Cached input is subtracted from input once, and reasoning is charged separately from visible output. Some counts are local estimates, so the currency is a consistent relative measure rather than a bill.
- **One generic victory-trend interface, score provider first.** v1 ships the smoothed, phase-gated score ratio behind the interface; the external civ-bench connector implements the same interface later.

## Stages

The executable workflow comes first, then signals, versioning, and the orchestrator.

| 1 | [01-scripted-strategist.md](01-scripted-strategist.md) | **Workflow format, minimal runtime, and `scripted-strategist` (null/none end-to-end).** The on-disk format (`workflow.ts` plus `subagents/*.json` plus `prompts/*.md`) and a path-based loader. A runtime that runs the script in `js-exec` with host primitives through `invokeTool`, the workflow definition mounted read-only, and a timeout raised for workflow runs while a compute bound stays. Each run opens one **run session** over the seat workspace and commits it once at the end. A keyed `seededIndex` primitive matches the static `null`'s choices exactly. Plugged into `VoxPlayer` and the registry as `scripted-strategist`. A completed script with no actions is a successful no-op; only script failure closes the run to actions and falls back to `keep-status-quo`. | 2 | [02-subagents.md](02-subagents.md) | **Sub-agent execution.** Manifest fields (role, tier, reasoning effort, prompt template, action/read/write allowlists, output file, budget) mapped onto `modelTiers`, the `@effort` suffix, and `getActiveTools`. **Scoped filesystem views** per invocation enforce each manifest's file grants for its shell tool and its template reads. The markdown **template engine** interpolating `records/` files via `jsonToMarkdown`; auto-write of free-text responses into the run session (visible to the script and later children at once) and through `recordBriefing`. The **cost currency** as a coefficient config over the normalized step counts. **Per-step ledgers** for per-sub-agent and per-run budgets, bounded overshoot for parallel children, refusal of new invocations after exhaustion, and a bounded final response through the existing nudge and tool narrowing. **Parallel sub-agent calls** through a host-side fan-out primitive that requires distinct outputs, and **cancellation** of outstanding children before any fallback. Each signal is individually enable-able. Verified against a recent game's records. The **adoption gate** is static checks over script, manifest, and prompt references, then a **stubbed dry-run** (stubbed models and actions) against a recent `records/turn-N` snapshot and its decision context from the seat's store; on pass it advances the seat ref atomically. The dry-run harness doubles as the hand-authoring and development testbed. Verified by committing a hand-edited version that a live run pins and picks up mid-game. |
| 6 | [06-orchestrator-offline.md](06-orchestrator-offline.md) | **Offline orchestrator agent and console cycle.** The orchestrator as a registered agent with file-edit and scoped-git sub-agents and tools (and a reserved judge-sub-agent seam), driven by an offline console in the oracle/telepathist family. ## How it fits the existing code

- **It plugs into the turn loop unchanged.** `scripted-strategist` registers in `vox-agents/src/infra/agent-registry.ts` and runs behind `vox-agents/src/strategist/vox-player.ts`'s pause, refresh, pace, decide, resume machinery, using `VoxContext`'s `withRun`/`forkRun` and token sink in `vox-agents/src/infra/vox-context.ts`. No new turn machinery.
- **Scripts run in the workspace shell's sandbox.** `PlayerWorkspace` (`vox-agents/src/utils/workspace/player-workspace.ts`) already enables `js-exec` over the seat's mounts, but opens each command against a fresh snapshot. The runtime adds a run session that stays open for a whole run, scoped views over it for each sub-agent, an `invokeTool` handler for host primitives, and a read-only mount of the pinned workflow definition.
- **Game state comes from the records the seat already keeps.** `SeatRecords.recordTurn` writes the knowledge reports behind `get-players`, `get-cities`, `get-military-report`, `get-options`, `get-victory-progress`, and `get-events` to `records/turn-N/`, and `get-options` also defines the decision-coverage inventory. The decision context `VoxPlayer` prepares after that (merged events, last decision turn) moves into one shared builder whose output is recorded beside them.
- **The equivalence oracle already exists.** The static strategists' `getSystem` (rendering the built-in templates in `vox-agents/prompts/`) and `getInitialMessages` are canonical for the Stage 3 bootstrap tests.
- **The prompt template engine reuses `jsonToMarkdown`** in `vox-agents/src/utils/tools/json-to-markdown.ts`, the one converter for rendering game-state files into prompts.
- **Sub-agents reuse the model and step machinery.** Tiers resolve through `modelTiers` and `selectModelReference`, effort through the `@effort` suffix, and budget exhaustion through `continuationNudge` and `activeTools` narrowing.
- **Telemetry stays the source of truth.** The SQLite span pipeline in `vox-agents/src/utils/telemetry/schema.ts` already carries input, cached, reasoning, and output tokens; the cost currency is a coefficient config over those attributes, and run transcripts are rendered from spans the way `vox-agents/src/oracle/retriever.ts` reads them.
- **The orchestrator console mirrors oracle and telepathist** in `vox-agents/src/oracle/console.ts` (and telepathist's persistent, database-backed conversation), reuses the cached MCP tool-definition snapshot for the schema surface, and reuses `executeAgent`'s compaction.
- **Cross-turn state in `game/` replaces `workingMemory`.** It stays per game, and it is the scripted counterpart of `StrategistParameters.workingMemory` (focus-briefer and episode requests) in `vox-agents/src/strategist/strategy-parameters.ts`.
- **Config resolution reuses `vox-agents/src/utils/config.ts`** (`configsDir`, `telemetryDir`), the `config.llms` model registry, and per-player `PlayerConfig.llms` overrides.
- **mcp-server is essentially unchanged.** The runtime calls existing action tools (`set-flavors`, `set-research`, `keep-status-quo`, and the rest).

## Risks and watch-items (resolved inside the relevant stages)

- **Parallel calls across the sandbox (Stages 1 and 2).** `invokeTool` calls look synchronous inside QuickJS, so a script cannot fan out by awaiting several promises. Parallel briefers need one host-side primitive that takes a batch of sub-agent calls and runs them concurrently.
- **Timeouts for LLM-awaiting scripts (Stage 1).** The default `js-exec` timeout is far shorter than a turn of LLM calls. Workflow runs need a longer wall-clock limit while a compute bound still kills a `while (true)` in plain code.
- **The host primitive surface is a trust boundary (Stages 1 and 2).** Scripts reach the host only through `invokeTool`, and action allowlists are enforced there, so keep that surface narrow and audited.
- **File grants live below `invokeTool` (Stage 2).** Sandbox file calls, a child's shell tool, and template reads each reach files by their own path, so grants are enforced in per-invocation scoped views. Building a view must never change the seat-wide workspace other agents are using.
- **Write visibility within a run (Stages 1 and 2).** Per-command snapshots would hide a child's output from the running script. The run session must make every write visible at once, reject colliding outputs in a parallel batch, and commit once at the end.
- **Live budgets (Stage 2).** Today a run's tokens are credited after the agent finishes. Budgets need per-step charging, a known overshoot bound for parallel children, refusal after exhaustion, a bounded final response, and cancellation of children before any fallback; a runaway LLM loop and a `while (true)` must both die.
- **Equivalence depends on derived context (Stages 1 and 3).** Records alone miss the merged events and last decision turn, so the decision context is recorded through one shared builder. `null` must keep its keyed `seededIndex`, and `none` must stay a no-op with no fallback call.
- **Version pinning against live commits (Stages 5 and 7).** A run reads its seat ref once at start; the atomic ref advance is what keeps an adopted edit off the run in flight.
- **Conversation growth across cycles (Stage 6).** Existing compaction protects initial messages, and a restored history arrives as initial messages, so the orchestrator needs its own rollover and a test across several resumed cycles.
- **The orchestrator boundary is enforced (Stages 6 and 8).** Scoped git access must not become a path to mcp-server or a game action; the "cannot act" test is a first-class deliverable.

## Verification (high level; per-stage detail comes later)

- **Per stage:** mock-tier Vitest for the runtime, host primitives, template engine, budgets, equivalence, gate static checks, and the boundary test; the stubbed dry-run (Stage 5) verifies control flow, rendering, and budget wiring without spending tokens.
- **End-to-end:** a `scripted-strategist` completing a full game with pacing, actions, telemetry, termination, and crash recovery unchanged (real and live tiers); and an offline orchestrator cycle committing a versioned, changelogged edit that a later run pins and adopts.
- **Acceptance for the workflow half:** every v1 roster member passes its one-time bootstrap equivalence test.
- **Acceptance for the orchestrator half:** a committed edit lands on a later run without blocking any strategist, its changelog cites the signals it read, and the boundary test proves no mcp-server and no action reach.
